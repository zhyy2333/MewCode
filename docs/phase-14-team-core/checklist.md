# Phase 14A 持久团队核心 Checklist

> 每项都通过运行代码或观察外部行为验证。实现文件、类名或内部函数调整时，只要系统行为不变，本清单仍然有效。开发完成后逐项记录命令输出、测试结果或观察证据；有一项未通过就不得宣告 Phase 14A 验收完成。

## Spec 行为验收

### 团队入口、挂载与仓库绑定

- [ ] **C01 / AC1 — 工具可见性矩阵正确。** 未创建团队、存在多个团队、已挂载和已卸载四种状态下，普通主 Agent 始终只有同一结构的团队生命周期入口；只有活动 Lead 看见成员管理、任务和邮箱能力，普通子 Agent与团队成员均无越权入口。（验证：依次构造五种 Agent 身份并捕获下一次模型请求的工具 schema，比较工具名和参数结构。）
- [ ] **C02 / AC2 — 团队名称和持久清单可靠。** 合法团队在应用重启后仍可按名称列出负责人、仓库、花名册和持久位置；大小写别名、保留名称、路径穿越和超长名称均在创建任何团队文件前失败。（验证：使用隔离用户目录运行创建—退出—重启—列出场景，并在每次非法创建后检查目录树没有新增团队。）
- [ ] **C03 / AC3 — Git 仓库绑定不可替换。** 非 Git 目录、其他仓库及伪造成员 Worktree 均不能创建或挂载团队；仓库移动后只有显式验证同一持久证明才能重新关联。（验证：在两个临时 Git 仓库及一个普通目录中交叉执行创建、挂载、替换和移动场景，观察明确错误及重新关联结果。）
- [ ] **C04 / AC4 — 同一团队只有一个活动 Lead。** 两个进程并发挂载时只有一个成功；有效租约期间不能接管，达到过期阈值并二次确认后新 Lead 才能成功，旧 Lead 随后不能写入。（验证：使用可控时钟和两个独立服务实例并发挂载，推进 59 秒和 60 秒边界并尝试双方状态更新。）
- [ ] **C05 / AC5 — Lead 升格、降格和卸载门禁生效。** 挂载后从下一次模型请求加入 Lead 能力，卸载后从下一次请求移除；存在运行中、排队中或活动恢复成员时卸载失败并列出准确成员。（验证：记录挂载/卸载前后连续模型请求的工具集，并分别制造三类阻止状态执行卸载。）
- [ ] **C06 / AC6 — 重新挂载恢复团队索引状态。** 卸载并重启后，花名册、任务、未读邮件、审批状态和持久待运行队列与退出前一致，不需要重新创建成员。（验证：准备包含上述五类数据的团队，完全销毁应用对象后重新挂载并逐项比较稳定 ID、状态和顺序。）

### 成员创建、角色与生命周期

- [ ] **C07 / AC7 — 成员身份、冻结角色和固定目录稳定。** 新成员具有唯一名称、冻结角色版本、固定 Worktree、进程内后端、审批标志及恢复位置；修改角色源文件不会改变成员，显式刷新后才产生新版本。（验证：创建成员、记录摘要、修改角色源、重启并再次读取，随后显式刷新并比较版本及能力变化。）
- [ ] **C08 / AC8 — 不支持的后端明确失败且不降级。** 请求终端窗格、独立进程或未知后端均报错，花名册、邮箱、会话和 Worktree 中不出现降级成员或残留资源。（验证：对每种非法后端执行新增成员并比较操作前后的团队状态和磁盘目录。）
- [ ] **C09 / AC9 — 成员创建全成或全败。** 在角色解析、名称注册、Worktree、邮箱、会话和状态发布处逐点注入故障，均不留下可挂载的部分成员，既有成员不受影响。（验证：逐个故障点执行创建，重启后检查花名册、注册表和资源目录，并确认原成员仍可收信。）
- [ ] **C10 / AC10 — 成员状态机只接受合法转换。** 创建、排队、运行、等待审批、空闲、停止、中断和失败状态均可观察；每种非法跳转都保持原状态并返回稳定错误。（验证：对状态转换表逐边执行允许和拒绝用例，比较操作前后成员状态、活动运行和运行代际。）
- [ ] **C11 / AC11 — 空闲与停止语义分离。** 自然结束进入空闲；显式停止保留上下文、邮箱和 Worktree，普通消息只入邮箱不恢复，Lead 显式恢复后才再次运行。（验证：分别让成员自然结束和运行中停止，再发送消息并观察队列/运行状态，最后显式恢复。）
- [ ] **C12 / AC12 — 成员安全移除保护成果。** 活动成员必须先停止；干净成员可注销和清理；存在未提交或未合并成果时 Git 状态不被修改，现场保留并返回安全路径和原因。（验证：对活动、干净、未提交、未合并四种成员分别执行移除，前后比较 `git status`、分支和目录。）
- [ ] **C13 / AC13 — 花名册和统一容量上限生效。** 第 32 位成员可创建、第 33 位失败；普通子 Agent和团队成员合计最多 8 个活动模型运行，等待成员按持久 FIFO 启动。（验证：使用可控模型运行闸门创建 33 位成员并同时请求超过 8 个运行，记录启动和释放顺序。）
- [ ] **C14 / AC14 — 同成员并发事件收敛到单运行。** 消息唤醒、显式恢复和容量释放竞争时最多启动一次；停止与启动竞争最终只有一个有效终态。（验证：用同步栅栏同时触发四类事件，统计运行 ID、运行代际和最终状态，多次重复测试。）

### 共享任务与依赖

- [ ] **C15 / AC15 — 任务 CRUD 与参与者权限正确。** Lead 和成员可创建、查看及修改合法任务；成员只能删除未开始且未被引用的任务，负责人可更新本人进度和结果，Lead 可合法重置及重新指派。（验证：以 Lead、负责人、非负责人三种身份执行完整动作矩阵并比较任务状态。）
- [ ] **C16 / AC16 — 过期任务修订不能覆盖新状态。** 两个参与者基于同一修订并发更新时只有一个成功，失败方收到当前版本和冲突信息。（验证：用并发栅栏提交两个不同更新，重读任务并确认只包含成功写入且修订只递增一次。）
- [ ] **C17 / AC17 — 依赖图拒绝非法引用和环。** 合法依赖链可保存，自依赖、重复依赖、未知任务和直接或间接依赖环均在写入前失败。（验证：构造长度 1、2 和多节点图，逐种提交后重读任务图。）
- [ ] **C18 / AC18 — 阻塞状态随依赖变化正确重算。** 上游未完成、失败或取消时下游不可领取；完成后立即可领取；修改依赖或重新打开上游后阻塞结果再次更新。（验证：按状态序列变更上游并在每一步读取下游的 blocked、blocking IDs 和 claimable。）
- [ ] **C19 / AC19 — 任务始终单负责人。** 多成员并发领取同一可运行任务只有一个成功，Lead 指派或重新指派后任何时刻只显示一位负责人。（验证：并发领取后读取任务及所有成员当前任务，再执行两次重新指派检查旧负责人清理。）
- [ ] **C20 / AC20 — 删除约束不会被绕过。** 进行中任务和仍被依赖的任务删除失败且状态不变；取消或重置并解除依赖后才可删除。（验证：对两种受保护任务执行删除，比较修订和依赖图，再完成前置操作重试。）
- [ ] **C21 / AC21 — 任务变化产生正确结构化通知。** 指派后目标成员收到任务指派消息；完成、失败或取消后 Lead 收到任务状态消息，下游可运行性同步更新。（验证：执行四种任务变化，读取目标邮箱协议字段并重读依赖任务视图。）
- [ ] **C22 / AC22 — 成员自然结束不自动完成任务。** 成员在任务仍进行中时自然停下只转为空闲；任务保持进行中，Lead 的空闲通知明确标识任务未完成。（验证：让模拟模型自然结束且不调用任务终态动作，随后读取成员、任务和 Lead 邮箱。）

### 邮箱、广播与唤醒

- [ ] **C23 / AC23 — 注册名称决定可投递目标。** Lead 和有效成员可按名称收信；未知、已移除、其他团队或伪造名称在写邮箱前失败。（验证：对五类收件人逐一发送，并比较所有邮箱日志的记录数。）
- [ ] **C24 / AC24 — 消息字段、默认值和大小限制正确。** 合法消息落盘后包含唯一 ID、发送者、目标、摘要、正文、协议、系统时间戳及未读状态；空/多行摘要、超长正文或错误载荷不产生记录。（验证：以边界长度前后各一个字符发送，重启后读取原始消息视图和邮箱计数。）
- [ ] **C25 / AC25 — 点对点和广播收件范围准确。** 点对点只进入目标邮箱；广播为除发送者外的每个有效参与者创建独立投递，并返回逐目标结果。（验证：建立 Lead 加三个成员，分别点发和广播，比较四个邮箱及返回的 correlation/result 集合。）
- [ ] **C26 / AC26 — 固定协议和方向严格执行。** 七种合法协议均可投递；未知协议、未知字段、错误类型以及方向非法的计划申请、审批决定、空闲通知和停止请求全部拒绝。（验证：对每种协议运行一个合法样本和一组畸形/反向样本，确认失败时无状态或邮箱变化。）
- [ ] **C27 / AC27 — 并发邮箱写入完整且无死锁。** 多发送者写同一邮箱时每条消息完整并按提交顺序可重放；不同邮箱可并行写入，所有操作在测试期限内结束。（验证：并发发送带序号消息，重启后核对 ID 集合、顺序和 JSON 完整性，并设置死锁超时断言。）
- [ ] **C28 / AC28 — 邮箱锁重试与旧锁回收符合时限。** 活动锁持续存在时调用方在可控 5 秒后明确失败；超过 30 秒且无活动 OS 锁的旧文件可回收，活动 OS 锁绝不能因文件年龄被删除。（验证：使用替代时钟分别模拟活动锁、旧文件和旧但仍活动三种情况。）
- [ ] **C29 / AC29 — 消息和广播崩溃恢复幂等。** 在写入前后及广播各目标边界崩溃后，已报告成功的收件人各有且仅有一条完整消息；同 ID 重试和部分失败重试不复制成功记录。（验证：逐故障点重启并重放相同投递，统计每个 message ID 和目标组合。）
- [ ] **C30 / AC30 — 未读顺序、回执和上下文提交关系可靠。** 未读消息顺序确定；标记已读后重启仍保持；写入成员上下文前崩溃的消息仍未读。（验证：固定时钟发送多条消息，在提交前/后中断，重启后比较邮箱回执和成员历史中的消息 ID。）
- [ ] **C31 / AC31 — 空闲成员唤醒可合并且容量不足不丢信。** 快速点发和广播后每个空闲目标最多恢复一次并批量收到全部消息；容量满时消息先落盘、唤醒进入队列，释放后恢复。（验证：占满 8 个名额后发送多封消息，记录邮箱、队列和后续运行批次。）
- [ ] **C32 / AC32 — 运行中收信只在安全边界出现。** 模型响应或工具调用期间到达的邮件不取消当前操作、不实时流式转发，只在下一模型边界进入上下文。（验证：用可暂停模型和工具分别制造在途操作，在中间投递消息并记录调用/事件时间线。）

### 计划审批与权限

- [ ] **C33 / AC33 — 未批准成员只有只读调研和计划能力。** 需审批成员领取新任务后可读代码、任务和邮箱，但写文件、Git 修改、命令副作用及其他副作用全部拒绝；提交带任务和递增版本的计划后进入等待审批。（验证：按工具安全类别执行允许/拒绝矩阵，提交计划后读取成员状态、审批记录和容量占用。）
- [ ] **C34 / AC34 — 审批决定只能由 Lead 作出并绑定新计划。** 非 Lead 无法决定；驳回必须有反馈且不开放副作用；成员提交新版本并收到对应批准后才能实施。（验证：分别以普通成员、申请成员和 Lead 发送决定，观察消息、审批版本及副作用执行结果。）
- [ ] **C35 / AC35 — 旧批准不能跨任务或变更复用。** 其他任务、旧计划版本、重新指派、任务重置和依赖变化后的批准均无法开工，必须重新申请和批准当前版本。（验证：对每种失效原因保留旧 approval ID 并尝试同一副作用，确认全拒绝后提交当前计划重试。）
- [ ] **C36 / AC36 — 批准不扩大角色和全局权限。** 获批成员仍不能调用冻结角色未包含、规则拒绝、工作区外或全局禁止的能力。（验证：为四类限制各准备一个操作，在有效批准前后比较结果，确保只有原本合法的副作用变化为可执行。）
- [ ] **C37 / AC37 — 审批异常一律保守拒绝。** 缺失、损坏、版本不匹配或检查异常时，成员仍能使用合法只读能力，但所有需审批副作用均不放行。（验证：逐种破坏审批读取路径，执行一项读取和一项写入并比较结果及状态完整性。）

### 完整上下文、空闲与异常恢复

- [ ] **C38 / AC38 — 成员完整上下文相互隔离并可压缩恢复。** 两个成员并行多轮模型、文件和工具操作并触发压缩后重启，各自只恢复自己的消息、结果、任务、审批及压缩摘要。（验证：给两名成员写入可区分标记，重启恢复后检查双方模型输入和持久历史不交叉。）
- [ ] **C39 / AC39 — 只恢复完整模型与工具边界。** 在模型流中、工具执行中、完整模型响应后及完整工具结果后中断，恢复时前两者不被视为完成，后两者完整保留。（验证：对四个中断点分别销毁进程状态并重启，对比恢复历史和下一模型提示。）
- [ ] **C40 / AC40 — 空闲通知发生在最终上下文持久化之后。** 自然结束后先可从磁盘恢复最终上下文，再看到 IDLE；Lead 邮箱收到成员、当前任务、任务状态和有界摘要。（验证：在收尾步骤间设置观察点，逐步检查会话、成员状态和 Lead 邮箱的可见顺序。）
- [ ] **C41 / AC41 — 跨应用继续同一长期成员。** 完全退出后重新挂载并给空闲成员发消息，成员无需重新派生即可恢复原 ID、完整历史、固定 Worktree、当前任务和有效审批。（验证：记录所有稳定标识和 Git 目录，销毁并重建应用对象后唤醒，逐字段比较及观察首轮恢复提示。）
- [ ] **C42 / AC42 — 成员运行失败局部隔离。** 模型、工具或上下文失败只使对应成员 FAILED 并通知 Lead，当前任务不自动完成；其他成员、Lead 会话和共享任务仍可操作。（验证：对三类失败分别注入异常，随后由另一成员收信和更新任务。）
- [ ] **C43 / AC43 — 异常退出恢复为中断且不重放副作用。** 运行中异常退出或正常关闭超时后，重新挂载显示成员 INTERRUPTED/可恢复并通知 Lead，最后一个不确定步骤没有自动重放。（验证：在副作用工具完成状态不确定时杀死测试进程，重启后统计工具调用次数和成员状态。）
- [ ] **C44 / AC44 — 挂载按需加载成员历史且损坏隔离。** 大型休眠历史不会在挂载时整体读取，只在唤醒该成员时加载；该历史损坏不影响其他成员运行。（验证：用带读取计数的存储替身挂载团队，再损坏一个成员日志并运行另一成员。）

### 安全、诊断与兼容性

- [ ] **C45 / AC45 — 路径和仓库替换攻击不能越界访问。** 路径别名、符号链接、重解析点、大小写变体及替换后的 Git 元数据均被拒绝，系统不读取或写入目标团队/仓库/工作区外文件。（验证：为每类攻击放置访问哨兵文件，执行操作后检查哨兵内容、访问计数和错误标识。）
- [ ] **C46 / AC46 — 同级内容始终是不可信输入。** 任务说明、邮箱正文和协议载荷中的伪造系统指令或提权请求不能改变模型消息优先级、工具范围、审批或权限。（验证：注入带唯一标记的恶意内容，捕获 Provider 请求角色和可用工具并尝试被请求的越权动作。）
- [ ] **C47 / AC47 — 日志和错误不泄露敏感上下文。** 终端、错误输出和日志只包含有界摘要及安全标识，不包含完整成员历史、工具参数、凭据、原始模型响应或异常堆栈。（验证：在输入中放置秘密哨兵并触发各类错误，递归搜索捕获输出和日志，秘密字符串必须为零命中。）
- [ ] **C48 / AC48 — 损坏或新版本团队拒绝写入且局部隔离。** 一个团队元数据损坏或版本未知时保留原现场并拒绝写入，其他团队和普通对话仍正常。（验证：复制损坏前文件哈希，尝试挂载/写入后确认哈希不变，再操作另一个团队和普通会话。）
- [ ] **C49 / AC49 — 三平台进程内语义一致。** Windows、macOS 和 Linux 均能完成创建、任务协作、邮箱唤醒、停止及跨重启恢复，不依赖终端分屏。（验证：在三平台 CI 运行同一端到端用例并保存各平台结果；不得以平台跳过掩盖功能缺失。）
