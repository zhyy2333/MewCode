# Phase 14A 持久团队核心 Spec

## 背景

MewCode 已支持主 Agent 委派短生命周期子 Agent，并可通过 Git Worktree 隔离其工作目录。但现有子 Agent 的任务状态、内部上下文和完成通知主要属于当前进程；不同子 Agent 之间没有共享任务清单、邮箱或长期成员身份，应用重启后也不能按原上下文继续协作。

Phase 14A 引入持久团队核心。普通主 Agent 可创建或挂载一个长期团队并就地成为 Team Lead；团队成员拥有固定身份、角色、Git Worktree、审批策略和可恢复会话。Lead 与成员通过共享任务和持久邮箱协作，成员空闲后仍保留在花名册中，收到后续消息即可继续运行。

本阶段只提供进程内成员后端。终端窗格后端及自动选择属于 Phase 14B；自动拆解目标、Git 汇总合并和 coordinator 模式属于 Phase 14C。

## 目标

- 让多个团队长期保存在用户环境中，同时保证一个主对话只挂载一个团队、一个团队同一时刻只有一个活动 Lead。
- 让每位成员绑定当前 Git 仓库中的长期 Worktree，并跨任务、跨应用重启保留完整可继续上下文。
- 让 Lead 和团队成员通过带简单依赖的共享任务清单及持久邮箱直接协作。
- 让需要审批的成员先只读调研并提交计划，获得针对该任务及计划版本的批准后才能产生副作用。
- 让自然完成的成员进入空闲状态并通知 Lead；后续点对点消息或广播可自动恢复空闲成员。
- 在统一并发预算、持久队列、锁竞争、异常退出和未合并成果保护下保持状态一致。
- 保持普通主 Agent、普通子 Agent及现有委派功能的行为和工具可见性兼容。

## 功能需求

### 团队生命周期与 Lead 升格

- **F1：** 普通主 Agent 始终只获得一个结构稳定的团队生命周期入口，用于创建、列出、挂载和卸载团队。普通子 Agent 不获得该入口。
- **F2：** 团队名称在当前用户范围内唯一，并经过大小写、路径字符和保留名称校验。每个团队在用户数据目录中拥有按团队名隔离的持久区域。
- **F3：** 团队持久状态至少记录名称、负责人、绑定仓库、创建与更新时间、花名册、状态版本及实际持久化位置。
- **F4：** 创建团队时必须绑定当前 Git 仓库身份和主工作区。来自其他仓库的挂载必须失败；仓库移动后只能通过显式重新关联并验证身份来恢复。
- **F5：** 一个主对话同一时刻只能挂载一个团队；一个团队同一时刻只能拥有一个活动 Lead。并发挂载必须通过独占租约确定成功者，失败方收到明确错误，不得抢占有效租约。
- **F6：** 挂载成功后，从主 Agent 的下一次模型请求开始进入 Lead 上下文并获得团队工具；卸载后从下一次请求恢复普通主 Agent 工具。卸载时若仍有运行中或待运行成员，操作必须失败并列出阻止原因。
- **F7：** 重新挂载团队时恢复花名册、任务、邮箱、待运行队列、审批状态及成员会话，并报告上次退出留下的中断状态。

### 工具隔离与花名册

- **F8：** 活动 Lead 获得成员管理、共享任务和邮箱能力；成员获得共享任务、邮箱及其冻结角色允许的普通工作能力。普通主 Agent、已卸载的主 Agent和普通子 Agent均看不到团队协作工具。
- **F9：** Lead 可新增成员。成员名称在团队内唯一；角色必须来自当前有效角色目录，并在创建时冻结提示、模型、工具范围、权限模式及版本标识。
- **F10：** 花名册为每位成员记录名称、冻结角色、固定工作目录、运行后端、是否需要审批、生命周期状态、当前任务和上下文恢复位置。
- **F11：** Phase 14A 只接受进程内后端。请求其他后端时必须明确失败，不得静默改用进程内执行。
- **F12：** 每位成员创建时获得当前团队仓库中的固定 Git Worktree。该目录跨任务、空闲和应用重启保持不变，不得退化为共享主工作区。
- **F13：** 成员创建必须是完整成功或完整失败；角色、邮箱、注册表、Worktree 或元数据任一步失败时，不得留下可被误认为有效成员的部分花名册记录。
- **F14：** Lead 可在成员空闲或已停止时显式刷新角色。刷新生成新的冻结版本并保留变更记录，不得在一次运行中途改变成员能力。
- **F15：** 成员至少具有创建中、待运行、运行中、等待审批、空闲、已停止、已中断和失败等可观察状态；非法状态转换必须被拒绝。
- **F16：** 自然结束的成员进入空闲状态；显式停止会取消当前运行并保留身份、上下文、邮箱及 Worktree，之后只能由 Lead 显式恢复。
- **F17：** 移除成员与停止成员分离。移除前必须结束活动运行并注销名称；Worktree 清理继续保护未提交或未合并成果，无法安全清理时保留现场并向 Lead 报告。
- **F18：** 团队花名册最多保留 32 位成员。团队成员与普通子 Agent 共用默认 8 个活动模型名额；容量不足的成员进入持久待运行队列，名额释放后按入队顺序启动。

### 共享任务

- **F19：** Lead 和成员可通过团队专属工具创建、读取、更新及删除共享任务。任务至少包含稳定标识、标题、说明、状态、负责人、依赖、创建者、时间信息和修订版本。
- **F20：** 并发更新必须基于修订版本检测冲突。过期写入不得覆盖较新的任务状态，并应返回当前版本供调用方重新决策。
- **F21：** 依赖只能引用同一团队中的现有任务；自依赖、重复依赖和依赖环必须在写入前被拒绝。
- **F22：** 任务只有在全部依赖完成后才可运行。依赖失败或取消时，下游保持阻塞，直到 Lead 修改依赖或重新打开相关任务。
- **F23：** 任务至少支持待处理、进行中、已完成、失败和已取消状态；“被依赖阻塞”作为可观察的运行条件，不替代任务自身状态。
- **F24：** 一个任务同一时刻最多有一位负责人。Lead 可直接指派或重新指派；成员可原子领取尚未指派且依赖已满足的任务。并发领取只能有一个成功者。
- **F25：** 所有成员可创建和读取任务，也可修改或删除尚未开始且未被引用的任务；任务负责人可更新自己任务的进度与结果；Lead 可执行所有合法指派、重置和状态转换。
- **F26：** 进行中任务不得直接删除，仍被其他任务依赖的任务不得删除。必须先取消或重置相关状态并解除依赖。
- **F27：** 指派或重新指派任务时，目标成员收到结构化任务消息；任务完成、失败或取消时，Lead 收到状态通知，下游任务的可运行状态随之重新计算。
- **F28：** 系统不得根据成员自然停下而擅自把任务标成完成。成员必须显式更新任务状态；空闲通知需同时说明当前任务是否仍未完成。

### 注册表与持久邮箱

- **F29：** 团队维护名称注册表，将 Lead 和每位有效成员映射到各自邮箱。向未知、已移除或不属于本团队的名称投递必须失败。
- **F30：** 每条消息至少包含唯一标识、发件人、目标、摘要、正文、协议类型、协议载荷、时间戳和已读状态。持久化时由系统补充时间戳，初始状态固定为未读。
- **F31：** 摘要必须是调用方提供的非空单行短文本；正文和协议载荷均执行大小限制与严格校验，不通过时不得产生部分消息。
- **F32：** Lead 和成员均可点对点发送消息。广播会向除发送者外的所有有效团队参与者分别创建持久投递，并返回每个收件人的结果。
- **F33：** Phase 14A 固定支持普通消息、任务指派、任务状态通知、计划审批申请、审批决定、成员空闲和停止请求。未知协议、未知字段或字段类型错误必须被拒绝。
- **F34：** 计划申请只能由需审批成员发给 Lead；审批决定只能由 Lead 发给申请成员；成员空闲通知由系统代表成员发给 Lead；停止请求只能由 Lead 发给成员。
- **F35：** 邮箱写入必须通过收件人级锁串行化。锁竞争时执行有界重试；超过规定期限的旧锁可被回收。最终拿不到锁时应明确失败，不得无锁写入。
- **F36：** 投递只有在消息完整持久化后才报告成功。使用消息唯一标识防止重试造成重复投递；广播部分失败时必须报告成功与失败收件人，重试不得复制已经成功的消息。
- **F37：** 收件人可按确定顺序列出未读消息、读取消息并标记已读；已读状态和未读顺序跨应用重启保留。
- **F38：** 点对点消息会自动唤醒空闲收件人，广播会唤醒所有空闲目标。同一成员短时间收到多封消息时合并为一次恢复运行；已停止或已移除成员不自动恢复。
- **F39：** 运行中成员收到的新消息只在下一个安全模型边界加入上下文，不打断当前模型响应或工具调用。本阶段不提供成员间实时流式通信。
- **F40：** 容量不足时，邮件仍先持久化，唤醒请求进入待运行队列；不得因暂时无并发名额而丢失或自动标记邮件已读。

### 计划审批

- **F41：** 标记为需要审批的成员，每个新任务都必须单独获批。批准与任务标识及计划版本绑定，不得复用于其他任务或其他版本。
- **F42：** 获批前，成员只能读取工作区、共享任务和邮箱，并可撰写或修改计划；所有写文件、修改仓库、执行有副作用命令及其他副作用能力都必须被拒绝。
- **F43：** 成员通过结构化计划申请提交任务、递增版本、计划正文和摘要，然后进入等待审批状态。
- **F44：** Lead 必须通过结构化审批决定明确批准或驳回对应申请。批准后成员恢复该冻结角色原有的合法能力；驳回必须附带反馈，成员修改计划并提交新版本后才能再次等待批准。
- **F45：** 计划发生实质修改时，已有批准失效。任务被重新指派、重置或替换依赖时，该任务尚未使用的批准也失效。
- **F46：** Lead 的批准只能解除“计划待审批”这一层限制，不能扩大成员冻结角色的工具范围，也不能绕过权限规则、工作区边界或硬安全限制。

### 会话持久化、空闲与恢复

- **F47：** 每位成员分别持久化完整模型消息、工具结果、上下文压缩状态、当前任务、审批关联和恢复边界；成员之间及成员与 Lead 之间不得串线。
- **F48：** 会话只在完整模型响应或完整工具结果等安全边界提交。未完整结束的边界不得被当作已完成步骤恢复。
- **F49：** 成员自然结束且不再请求工具时，系统先持久化上下文，再把成员标记为空闲，并向 Lead 投递包含成员、当前任务、任务状态和有界结果摘要的空闲通知。
- **F50：** 向空闲成员成功投递消息后，系统从磁盘恢复其原有身份、完整上下文、固定 Worktree、冻结角色、当前任务和仍有效的审批状态，不创建新的花名册成员，也不要求重新派生。
- **F51：** 成员运行失败时保留会话和 Worktree，标记失败并通知 Lead；系统不得擅自把其当前任务改成完成。Lead 可在检查后显式恢复或停止该成员。
- **F52：** 应用异常退出或在成员运行期间关闭时，只承认最后一个完整持久化边界。下次挂载时将遗留运行状态改为已中断并空闲，通知 Lead，且不得自动重放可能产生副作用的步骤。
- **F53：** 同一个成员同时只能有一个活动运行或恢复动作。并发消息、显式恢复和容量释放发生竞争时必须合并，不能重复启动成员。
- **F54：** 团队成员不得调用普通 Agent 委派入口、团队生命周期入口或成员管理能力，也不能派生普通子 Agent或新的团队成员。

## 非功能需求

### 容量与性能

- **N1：** 普通主 Agent 的团队生命周期入口名称、说明和参数结构不得因团队数量、花名册或任务状态而变化；团队专属工具也不得把动态成员名或任务标识嵌入工具结构。
- **N2：** 单个用户最多保存 128 个团队；单团队成员上限为 32、活动模型运行上限继续使用统一的 8 个名额。
- **N3：** 团队名和成员名最长 64 个字符；任务标题最长 256 个字符、说明最长 64 KiB、单任务依赖最多 64 项。
- **N4：** 消息摘要最长 256 个字符；正文和编码后的协议载荷各不超过 64 KiB。超限输入必须在持久化或唤醒成员前失败。
- **N5：** 挂载团队不得把所有成员的完整历史一次性载入内存；只加载花名册、任务、邮箱索引和恢复元数据，成员完整上下文在实际恢复时按需读取。
- **N6：** 待运行队列遵循先进先出；单个失败或长期运行的成员不得阻止容量释放后其他成员启动，也不得通过忙轮询持续占用处理器。

### 持久化与并发一致性

- **N7：** 团队数据位于当前用户的 MewCode 数据区域，并按经过校验的团队名隔离。所有持久记录均带格式版本；遇到未知的更新版本时必须拒绝写入，不能按旧格式覆盖。
- **N8：** 团队元数据、花名册、任务、邮箱、待运行队列和成员恢复点的更新必须具有崩溃一致性。进程中断后只能观察到更新前或完整更新后的状态，不能观察到半条消息或半个成员。
- **N9：** 邮箱锁获取失败后最多重试 5 秒；锁年龄超过 30 秒时视为过期并允许安全回收。超过重试期限仍失败时，调用方必须收到明确错误。
- **N10：** Team Lead 租约至少每 10 秒续期一次；连续 60 秒未续期后才可视为过期。接管前必须再次确认租约未恢复，避免暂停或调度延迟造成双 Lead。
- **N11：** 不同收件人的邮箱写入可以并行；同一邮箱、共享任务清单和花名册的竞争更新必须串行化。锁获取顺序必须固定，避免操作之间形成死锁。
- **N12：** 每条消息按唯一标识至多追加一次。消息只有在已写入成员上下文的恢复边界完整持久化后才可标记已读；崩溃恢复不得遗漏消息，也不得把同一消息重复加入同一成员上下文。
- **N13：** 成员运行、消息唤醒、显式恢复、停止和容量释放之间的竞争必须收敛到单个状态转换及最多一个活动运行。
- **N14：** 损坏、截断或校验失败的持久文件不得被自动覆盖。系统应保留原始现场、拒绝相关写操作，并返回有界诊断，使其他未受影响团队仍可使用。
- **N15：** 正常退出最多等待 5 秒让活动成员到达安全边界；超时后取消运行并记录为中断。退出不得无限等待模型、工具、Git 或锁。

### 上下文与恢复可靠性

- **N16：** 完整会话持久化沿用现有上下文容量、压缩和归档规则；压缩不得丢失成员身份、未完成任务、未读消息、有效审批或关键工具结果。
- **N17：** 恢复后的首个模型请求必须明确标识这是原成员的继续运行，并提供中断原因、当前任务、待处理消息和审批状态；不得让模型误认为自己是新成员。
- **N18：** 运行失败、计划驳回、消息投递失败、锁超时或上下文损坏只影响对应成员或操作，不得破坏 Lead 会话、其他成员、共享任务或现有普通子 Agent。
- **N19：** 空闲通知、失败通知和恢复诊断均应限制长度，不得包含完整内部消息、完整工具参数、认证信息、未经处理的模型响应或异常堆栈。
- **N20：** 团队任务、消息和成员状态的时间顺序使用可测试的统一时钟；同一来源产生的事件保持顺序，并发来源允许按实际提交顺序交错。

### 安全与权限

- **N21：** 团队能力采用只会收窄的权限组合。Team Lead 身份、角色冻结、审批通过或消息协议均不能恢复被全局安全策略、工作区边界或权限规则禁止的能力。
- **N22：** 审批状态缺失、损坏、版本不匹配或无法确认时必须按“未批准”处理。审批检查失败不得降级为普通权限询问或默认放行。
- **N23：** 成员名称、团队名称、仓库身份和持久路径必须经过规范化及归属校验，拒绝路径穿越、链接逃逸、大小写别名和指向其他团队或仓库的替换。
- **N24：** 固定 Worktree 只提供 Git 工作目录隔离，不宣称是操作系统沙箱；现有路径安全检查和权限系统仍是阻止越界访问的硬边界。
- **N25：** 角色刷新必须产生可验证的新版本；损坏或不完整的新角色不得替换当前可用快照。
- **N26：** 所有邮箱正文、任务说明和结构化协议载荷均视为同级成员产生的不可信内容，不能覆盖系统规则、人工指令、审批限制或工具权限。
- **N27：** 持久会话采用与现有主会话相同的本地保密模型和敏感信息清理规则。本阶段不新增静态加密，但不得把会话内容复制到日志、终端摘要或其他成员邮箱。
- **N28：** 停止、移除、卸载和异常恢复均不得自动提交、丢弃、重置或覆盖成员 Worktree 中的 Git 变更。

### 兼容性与可测试性

- **N29：** 未创建或未挂载团队时，现有普通对话、PLAN、权限、Hook、MCP、Skill、普通子 Agent及 Worktree 子 Agent行为保持兼容，不产生团队后台任务或团队文件写入。
- **N30：** Phase 14A 在项目当前支持的 Windows、macOS 和 Linux 环境中提供相同的进程内团队语义；平台不支持终端分屏不影响本阶段。
- **N31：** 不可用或未知成员后端必须明确报错；任何启动、恢复或角色刷新路径都不得静默更换后端、工作目录、模型或权限模式。
- **N32：** 时钟、标识生成、锁、租约、Git、模型运行、容量调度和异常退出边界都必须支持替换为测试实现；并发、旧锁、消息去重和崩溃恢复测试不得依赖真实长时间等待。
- **N33：** 至少通过单元测试验证持久模型与状态转换，通过集成测试验证团队工具隔离、任务并发、邮箱唤醒和审批，通过端到端测试验证跨应用重启继续同一成员。
- **N34：** 新增用户可见状态和错误应保持稳定、简洁，并包含足以定位团队、成员、任务或消息的安全标识，不依赖内部异常文本。

## 不做的事

- 不实现独立终端窗格、终端复用器、独立进程成员、窗格唤醒或按环境优先级选择后端；这些属于 Phase 14B。
- 不在本阶段实现“Lead 自动把用户目标拆成完整依赖图、持续调度到全部完成”的专用编排循环。Lead 可以使用任务工具进行人工智能决策，但系统不保证自动闭环。
- 不自动合并成员 Worktree，不自动解决或回滚 Git 冲突，也不判断整个用户目标是否已经完成；这些属于 Phase 14C。
- 不实现 coordinator 双开关，也不剥夺 Lead 的写文件工具；coordinator 的能力门禁和专用工具集属于 Phase 14C。
- 不支持跨机器、跨用户或云端同步团队；一个团队只存在于创建它的本地用户环境。
- 不支持多个活动 Lead、一个主对话同时挂载多个团队，或一个团队跨多个 Git 仓库工作。
- 不支持非 Git 团队、任意外部成员目录、共享主工作区成员或每任务更换 Worktree。
- 不允许成员创建团队、派生成员、启动普通子 Agent或形成嵌套团队。
- 不支持多负责人任务、跨团队依赖、条件依赖、权重、优先级、截止时间、资源配额、投票或共识约束。
- 不根据成员自然结束自动完成任务，也不自动重试失败任务或自动重新指派。
- 不支持任意自定义消息协议、附件、二进制消息、成员间实时流式内容或已发送消息撤回。
- 不保证外部工具副作用恰好执行一次；系统只保证消息不会重复加入成员持久上下文，并在不确定时停止自动重放。
- 不监视角色文件变化，也不自动热更新长期成员；只能由 Lead 对空闲或已停止成员显式刷新角色。
- 不新增团队数据静态加密、密钥管理、远程备份或云端恢复。
- 不把 Git Worktree 描述为安全沙箱，也不提供容器、虚拟机或操作系统级成员隔离。
- 不提供强制清除含未合并成果的成员目录。
- 不在 Phase 14A 提供整队永久删除或批量强制清理；团队可卸载，成员可逐一安全移除。

## 验收标准

### 团队入口、挂载与仓库绑定

- **AC1：** 分别在未创建团队、存在多个团队、已挂载团队和已卸载团队时检查工具：普通主 Agent 始终只有同一结构的团队生命周期入口；只有活动 Lead 看见成员管理、任务和邮箱工具；普通子 Agent及团队成员均无法获得越权入口。（覆盖 F1、F8、F54、N1、N29）
- **AC2：** 创建合法团队后，重启应用仍可按名称列出并识别其负责人、绑定仓库、花名册和持久位置；尝试使用大小写别名、保留名称或路径穿越名称创建时均在写入前失败。（覆盖 F2、F3、N7、N23）
- **AC3：** 在非 Git 目录创建团队、从不同仓库挂载团队或用其他目录替换成员 Worktree 时均明确失败；移动原仓库后必须完成显式身份验证才能重新关联。（覆盖 F4、F12、N23、N24）
- **AC4：** 两个进程并发挂载同一团队时只有一个成为 Lead；有效租约存续期间另一方不能接管，租约过期并二次确认后才允许新 Lead 挂载。（覆盖 F5、N10）
- **AC5：** 主 Agent 成功挂载后从下一次模型请求获得 Lead 能力；卸载后从下一次请求失去这些能力。存在运行中或待运行成员时卸载失败，并准确列出阻止卸载的成员。（覆盖 F6）
- **AC6：** 卸载并重启应用后重新挂载，观察花名册、任务、未读邮件、审批状态和待运行队列与退出前一致；无需重新创建成员。（覆盖 F7）

### 成员创建、角色与生命周期

- **AC7：** 新增成员后可观察到唯一名称、冻结角色版本、固定 Worktree、进程内后端、审批标志和恢复位置；随后修改角色文件不会改变该成员，显式刷新后才产生新版本。（覆盖 F9、F10、F14、N25）
- **AC8：** 请求终端窗格、独立进程或未知后端时明确失败，花名册中不出现降级后的成员。（覆盖 F11、N31）
- **AC9：** 分别在角色无效、名称冲突、Worktree 创建失败、邮箱初始化失败和元数据提交失败处注入故障，均不留下可挂载的部分成员；已存在成员保持不变。（覆盖 F13、N8、N18）
- **AC10：** 让成员依次经历创建、排队、运行、等待审批、空闲、停止、中断和失败状态，观察所有合法转换可见；尝试非法跳转时状态不变并返回明确错误。（覆盖 F15）
- **AC11：** 自然完成后成员进入空闲；显式停止运行中的成员后，其上下文、邮箱和 Worktree 保留，普通消息不自动恢复，只有 Lead 显式恢复才重新运行。（覆盖 F16）
- **AC12：** 移除活动成员时先要求停止；移除干净成员时安全注销并清理；成员目录存在未提交或未合并成果时不改写 Git 状态，保留现场并报告位置与原因。（覆盖 F17、N28）
- **AC13：** 创建 32 位成员成功，第 33 位被拒绝；同时启动超过 8 个团队成员与普通子 Agent时最多只有 8 个模型运行，其余按入队顺序依次启动。（覆盖 F18、N2、N6）
- **AC14：** 消息唤醒、显式恢复和容量释放同时作用于同一成员时，只产生一个活动运行；停止与启动竞争也只收敛到一个有效终态。（覆盖 F53、N13）

### 共享任务与依赖

- **AC15：** Lead 和成员可创建、查看及修改合法任务；成员可删除尚未开始且未被引用的任务，负责人可更新自己的进度与结果，Lead 可执行合法重置与重新指派。（覆盖 F19、F25）
- **AC16：** 两个成员基于同一修订版本并发更新任务时只有一个写入成功，另一个得到冲突及最新版本，不会覆盖先成功的变更。（覆盖 F20）
- **AC17：** 分别创建合法依赖链、自依赖、重复依赖、未知任务依赖和依赖环；只有合法依赖链写入成功。（覆盖 F21）
- **AC18：** 上游未完成、失败或取消时下游保持不可领取；上游完成后下游立即变为可领取；Lead 修改依赖或重新打开上游后可重新计算阻塞状态。（覆盖 F22、F23）
- **AC19：** 多名成员并发领取同一未指派且可运行的任务时只有一人成功；Lead 可直接指派或重新指派，任何时刻任务只显示一位负责人。（覆盖 F24）
- **AC20：** 尝试删除进行中任务或仍被依赖的任务时操作失败且任务保持不变；取消并解除依赖后才可删除。（覆盖 F26）
- **AC21：** 指派任务后目标成员收到结构化任务消息；完成、失败或取消任务后 Lead 收到状态消息并观察下游可运行性更新。（覆盖 F27）
- **AC22：** 成员在任务仍为进行中时自然停下，成员变为空闲但任务不被自动完成；Lead 收到的空闲通知明确显示任务仍未完成。（覆盖 F28）

### 邮箱、广播与唤醒

- **AC23：** Lead 与每位有效成员都可通过注册名称收信；向未知、已移除、其他团队或伪造名称发送时在投递前失败。（覆盖 F29）
- **AC24：** 投递普通消息后，落盘记录具有唯一标识、发送者、目标、摘要、正文、协议、系统时间戳和默认未读状态；空摘要、多行摘要、超长正文或错误载荷不产生消息。（覆盖 F30、F31、N3、N4）
- **AC25：** 点对点消息只进入目标邮箱；广播分别进入除发送者外的所有有效邮箱，并返回逐收件人结果。（覆盖 F32）
- **AC26：** 七种固定协议的合法消息均可投递；未知协议、未知字段、错误字段类型以及方向不合法的计划申请、审批决定、空闲通知和停止请求均被拒绝。（覆盖 F33、F34、N26）
- **AC27：** 多个发送者并发写同一邮箱时消息均完整且顺序确定；不同邮箱可同时写入，不发生死锁。（覆盖 F35、N11、N20）
- **AC28：** 持有邮箱锁时发送方持续重试并在 5 秒后明确失败；将锁置为超过 30 秒的旧锁后可安全回收并完成投递。（覆盖 F35、N9）
- **AC29：** 在消息写入和广播各收件人写入的不同边界模拟崩溃，恢复后每个已报告成功的收件人恰有一条完整消息；使用同一消息标识重试不会重复追加，部分失败结果可安全重试。（覆盖 F36、N8、N12）
- **AC30：** 未读消息按确定顺序列出；读取并标记已读后重启应用，顺序及已读状态保持；消息写入成员上下文前发生崩溃时仍保持未读。（覆盖 F37、N12）
- **AC31：** 向多个空闲成员快速发送点对点消息和广播，观察每位目标成员最多恢复一次并批量收到所有消息；容量满时消息先持久化，成员进入队列，容量释放后恢复。（覆盖 F38、F40）
- **AC32：** 成员正在生成模型响应或执行工具时收到邮件，当前操作不被中断；新邮件只在下一安全模型边界出现，且不存在实时流式转发。（覆盖 F39）

### 计划审批与权限

- **AC33：** 需要审批的成员领取新任务后可读取代码、任务和邮箱，但所有写文件、Git 修改和其他副作用操作均被拒绝；提交带任务及递增版本的计划后进入等待审批。（覆盖 F41、F42、F43、N21、N22）
- **AC34：** 非 Lead 无法发送审批决定；Lead 驳回时必须提供反馈，原计划仍无副作用权限；成员提交新版本并收到对应批准后才能继续实施。（覆盖 F44）
- **AC35：** 用其他任务、旧计划版本、已重新指派任务或依赖已改变任务的批准尝试开工时均被拒绝；必须重新提交并批准当前版本。（覆盖 F41、F45）
- **AC36：** Lead 批准计划后，成员仍无法调用被冻结角色未包含、权限规则拒绝、工作区外或全局禁止的能力。（覆盖 F46、N21）
- **AC37：** 删除或损坏审批记录、制造版本不一致或审批检查异常时，成员保持未批准，只读能力仍可使用，副作用能力不被放行。（覆盖 N22）

### 完整上下文、空闲与异常恢复

- **AC38：** 让两个成员并行进行多轮模型、文件读取和工具操作，触发上下文压缩后重启；分别恢复时只看到自己的消息、工具结果、任务、审批和压缩摘要。（覆盖 F47、N16）
- **AC39：** 分别在模型流式响应中途、工具执行中途、完整模型响应后和完整工具结果后中断进程；恢复时只承认完整边界，不把半个响应或半个工具结果当作已完成。（覆盖 F48）
- **AC40：** 成员自然结束后，先能从磁盘恢复最终上下文，再观察到空闲状态；Lead 邮箱收到包含成员、当前任务、任务状态和有界摘要的空闲通知。（覆盖 F49）
- **AC41：** 彻底退出应用后，Lead 重新挂载团队并给空闲成员发消息；成员无需重新派生，即可从原身份、完整历史、固定 Worktree、当前任务和有效审批继续运行。（覆盖 F50、N17）
- **AC42：** 模型、工具或上下文运行失败时，只对应成员进入失败状态并通知 Lead；当前任务不被自动完成，其他成员、Lead 会话和共享任务仍可工作。（覆盖 F51、N18）
- **AC43：** 应用在成员运行时异常退出或超过关闭等待期限，重新挂载后该成员显示为已中断并空闲，Lead 收到说明；系统不自动重放最后一个不确定步骤。（覆盖 F52、N15）
- **AC44：** 为一个休眠成员准备大型历史、同时保留其他成员正常数据；挂载团队时不读取该成员全部历史，只有真正唤醒时才加载。该成员历史损坏时，其他成员仍可运行。（覆盖 N5、N14、N18）

### 安全、诊断与兼容性

- **AC45：** 尝试用路径别名、符号链接、大小写变体或替换后的 Git 元数据把成员指向其他团队、仓库或工作区外时，操作被拒绝且目标文件不被访问。（覆盖 N23、N24）
- **AC46：** 在任务说明、邮箱正文和协议载荷中放入伪造系统指令或提权请求，观察其仍作为不可信成员内容处理，不能改变工具、审批或权限边界。（覆盖 N26）
- **AC47：** 检查终端、错误输出和日志：只出现有界摘要及安全标识，不包含完整成员历史、工具参数、凭据、原始模型响应或异常堆栈。（覆盖 N19、N27、N34）
- **AC48：** 损坏一个团队的元数据或写入未知格式版本后，该团队拒绝写入并保留现场；其他团队及普通对话仍可正常使用。（覆盖 N7、N14、N18）
- **AC49：** 在 Windows、macOS 和 Linux 的测试环境中运行相同的进程内团队场景，均能完成创建、任务协作、邮箱唤醒、停止和跨重启恢复，不依赖终端分屏能力。（覆盖 N30）
- **AC50：** 未创建或未挂载团队时运行现有普通对话、PLAN、Hook、MCP、Skill、普通子 Agent和 Worktree 子 Agent测试，行为及工具可见性保持兼容，也不产生团队持久文件。（覆盖 N29）
- **AC51：** 使用替代时钟、锁、Git、模型和调度器运行旧锁、租约过期、并发领取、消息去重及崩溃恢复测试，无需真实等待规定时长或访问网络。（覆盖 N32、N33）
