# Phase 14B 隔离成员后端 Spec

## 背景

Phase 14A 已提供持久团队、固定成员身份与 Git Worktree、共享任务和邮箱、计划审批、长期会话恢复、进程内成员运行以及共享容量池。其团队领域模型、租约、邮箱、会话、调度器、容量和 Worktree 所有权语义是本阶段的既有基础，不得重新实现或破坏。

Phase 14B 为成员增加可隔离运行的终端窗格后端。隔离成员仍是同一长期团队成员：保留原有身份、工作目录、冻结角色、审批状态、任务、邮箱和会话；区别仅在于实际 MewCode 运行位于受管理的独立终端窗格中。

### 基线验证记录

- 2026-08-20：在干净工作树运行 `python -m pytest`，1068 项全部通过，耗时 31.46 秒。
- Phase 14A 的规格、实现和团队测试已核验。其 checklist 已保存自动化构建项的证据；更强的跨进程、三平台和端到端验收项仍保持未勾选，不将现有自动化测试等同于这些尚无证据的验收项。

## 目标

- 支持 Windows Terminal 窗格、tmux 窗格和既有进程内后端。
- 默认按平台和明确优先级选择后端：Windows 使用 Windows Terminal 后再使用进程内；macOS 和 Linux 使用 tmux 后再使用进程内。
- 显式请求后端时，后端不可用必须明确失败，绝不静默降级。
- 让隔离成员继续使用 14A 的长期身份、固定 Worktree、共享任务、邮箱、审批、会话恢复和容量池语义。
- 让持久邮箱投递可靠唤醒对应成员的终端窗格，并在成员自然停止、窗格消失、进程异常退出、重复唤醒和应用重启后保持可恢复性。
- 保持 Windows、macOS 和 Linux 上合理且明确的能力边界；不支持的终端能力必须提供诊断。

## 功能需求

- **F1：** 新增成员可选择自动、Windows Terminal、tmux 或进程内后端。自动选择为默认，并按既定的平台优先级解析；解析出的实际后端在成员生命周期内保持稳定。
- **F2：** 显式请求的后端必须可用且满足终端宿主条件。创建、恢复或启动不能满足时必须明确失败，且不得改用其它后端。
- **F3：** Windows Terminal 仅在 Lead 位于可识别的 Windows Terminal 当前会话时创建相邻窗格；tmux 仅在 Lead 位于当前 tmux 会话时创建相邻窗格。已安装但不在对应宿主中的终端不视为窗格后端可用。
- **F4：** 隔离成员在窗格中以受管理的工作模式运行完整 MewCode 成员能力，继续受冻结角色、权限、审批、固定 Worktree、共享任务、邮箱和长期会话约束，但不接受任意人工终端输入。
- **F5：** 每位隔离成员具有可验证的窗格关联。自然停止时成员 MewCode 进程结束并转为 IDLE，而窗格保留；后续唤醒优先复用原窗格，窗格缺失时自动创建替代窗格。
- **F6：** Lead 可以从成员列表观察成员的实际后端、窗格可用性和最近一次有界诊断；本阶段不增加独立的人工窗格管理动作。
- **F7：** 投递给隔离成员的点对点消息、广播或任务指派，必须继续经过现有名称注册表和持久邮箱，并可靠触发正确窗格的成员唤醒。
- **F8：** 同一成员的重复邮件、任务指派、显式恢复、容量释放和窗格唤醒必须合并，任意时刻最多一个实际成员模型运行。
- **F9：** 后续唤醒从磁盘恢复同一成员的原有身份、完整会话、当前任务、有效审批和固定 Worktree，不得创建新成员或新的长期上下文。
- **F10：** 窗格消失、成员进程异常退出、窗格控制失败和应用重启必须产生可操作诊断。运行中的异常退出继续采用 14A 的失败与不重放语义。
- **F11：** 邮件或任务已持久化后，如终端无法唤醒，系统必须报告“已投递、未启动”，不丢信、不自动降级，并将成员标记为 FAILED；Lead 可在环境恢复后通过既有恢复操作重试。
- **F12：** 未使用隔离后端的团队、既有进程内成员和全部非团队功能保持 14A 兼容行为。

## 非功能需求

- **N1：** 成员后端、窗格关联、唤醒记录和诊断等新增持久数据必须严格校验、原子更新并带格式版本；14A 已持久化的进程内成员可无迁移继续使用。
- **N2：** 未知的新格式、损坏状态或不可信窗格关联不得被自动覆盖或猜测修复；系统应保留现场并给出有界诊断。
- **N3：** 成员的实际后端不得因应用重启、当前终端变化或自动探测结果变化而静默漂移。
- **N4：** 终端控制能力必须在 Windows、macOS 和 Linux 上明确探测。当前平台、终端宿主、命令版本或权限不足时，错误应包含请求后端和不可用原因；自动选择仅可按既定顺序继续尝试。
- **N5：** 窗格宿主、成员 MewCode 进程与实际模型运行必须可区分；只有实际成员模型运行继续占用 14A 的统一容量名额，空闲窗格不得挤占容量。
- **N6：** 成员身份、冻结角色、审批、工作目录、任务和会话恢复的安全边界不得因跨进程启动而放宽；敏感配置不得出现在命令行、窗格标题、诊断或邮箱中。
- **N7：** 唤醒、窗格失效检测、子进程退出、重复请求、关闭和应用重启不得忙轮询，且必须具有确定、可测试的收敛结果。
- **N8：** 时间、标识、终端探测与控制、子进程、环境、Git、文件锁、容量和等待边界均必须可替换测试；测试不得依赖真实长时间等待或真实模型调用。
- **N9：** 终端和进程错误只能影响对应成员或本次操作，不得破坏 Lead、其他成员、共享任务、邮箱或既有进程内成员。
- **N10：** 用户可见状态和诊断必须简洁、稳定且不泄露完整上下文、工具参数、凭据、原始模型响应或异常堆栈。
- **N11：** 除 Windows Terminal 与当前 tmux 宿主外，不宣称支持其它终端原生分屏；其它情形必须返回明确的后端不可用诊断。

## 不做的事

- 不支持跨机器、跨用户、云端或远程终端成员。
- 不支持成员间实时流式通信、屏幕共享或人工接管成员 REPL。
- 不支持 Windows Terminal、tmux 之外的原生终端分屏。
- 不自动将已解析为终端后端的成员改为进程内运行。
- 不实现自动任务拆解闭环、自动 Git 合并、coordinator 模式或其它 Phase 14C 范围。
- 不把终端窗格或 Worktree 宣称为操作系统安全沙箱。

## 验收标准

- **AC1：** 自动选择在 Windows、macOS 和 Linux 上遵守既定优先级；显式后端不可用时明确失败且无降级。
- **AC2：** 仅在当前受支持的终端宿主中创建相邻窗格；非宿主环境的能力诊断准确。
- **AC3：** 隔离成员在独立窗格运行时保留其身份、Worktree、角色、审批、任务、邮箱与会话。
- **AC4：** 成员自然结束后为 IDLE、成员进程结束且窗格保留；后续唤醒复用原窗格，缺失时自动创建替代窗格并恢复原上下文。
- **AC5：** 点对点消息、广播和任务指派均先可靠写入既有邮箱，再精确唤醒目标隔离成员；重复唤醒只产生一次成员运行。
- **AC6：** 终端唤醒失败时，已持久化邮件与任务仍可观察，成员为 FAILED，Lead 获得“已投递、未启动”诊断；环境恢复后可通过既有恢复操作重试。
- **AC7：** 成员进程异常退出、窗格消失和 Lead 应用重启均保持 14A 的保守恢复与不重放语义。
- **AC8：** 旧的 14A 进程内持久状态可读取；新增格式严格校验，损坏或未来版本不会被覆盖。
- **AC9：** 成员列表准确显示实际后端、窗格状态和有界诊断；未使用隔离后端的行为不变。
- **AC10：** 单元、集成、崩溃恢复、并发和端到端测试覆盖上述场景；专项回归和完整测试套件通过，checklist 只勾选具有实际命令或观察证据的项目。
