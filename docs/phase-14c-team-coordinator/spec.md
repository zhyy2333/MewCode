# Phase 14C Team Lead 编排、受控 Git 集成与 Coordinator 双开关 Spec

## 背景

Phase 14A 已提供持久团队、长期成员身份、固定 Git Worktree、共享任务与邮箱、结构化审批、租约、容量和会话恢复。Phase 14B 已完成验收，为进程内、Windows Terminal 和 tmux 成员提供真实运行、唤醒、重连、恢复及保守终态收敛。

当前 Team Lead 可以人工使用这些能力，但还不能把用户目标稳定地拆成依赖任务、持续按成员角色与容量编排执行，或在全部成果满足安全条件后按依赖顺序集成 Git 提交。本阶段把团队升级为可恢复、可审计的交付单元，同时通过配置能力开关与用户环境变量共同控制这一高权限模式。

### 前置状态

- Phase 14B 的验收清单已经完整通过，因此本阶段覆盖进程内、Windows Terminal 和 tmux 三种成员后端。
- 如果以后加载的构建或运行环境不能证明 Phase 14B 已完成，自动拆解、派发和集成只能接受进程内成员；终端成员必须得到明确拒绝，不能静默降级，也不能把其结果视作可合并成果。
- 旧 Phase 14A/14B 团队状态仍是兼容输入；缺少任何 Phase 14C 文件表示 coordinator 从未启用。

## 目标

- Team Lead 能把一个用户目标拆成数量受限、依赖明确、可验收且可审计的共享任务。
- 系统能依据依赖、成员角色与能力、成员状态、审批条件、持有任务和共享容量安全派发，并在条件变化时重派、停止、取消或转人工。
- 系统能持续观察任务、成员、审批、邮箱、运行终态和 Git 成果，形成确定且可恢复的协调决定。
- 系统能把已验证任务形成稳定的集成批次，按依赖拓扑顺序检查并合并成员固定 Worktree 中的本地提交。
- 所有 Git 写操作都受仓库、Worktree、基线、命令和恢复策略约束；失败不留下未报告的部分成功，不触碰远端，也不删除未合并成果。
- Coordinator 只有在配置能力开关与用户环境变量同时启用时才生效，并在生效时收窄 Team Lead 的直接写入权限。

## 功能需求

- **F1：双开关与作用域。** Coordinator 必须同时满足配置能力开关已启用和用户环境变量明确启用。任一开关关闭时，专用动作不可见或明确拒绝，Team Lead 保持 Phase 14A/14B 的工具与权限，且不创建 coordinator 状态、journal 或后台协调任务。两个开关均开启时，限制只作用于已绑定团队的 Team Lead；普通成员、普通子 Agent 和未启用团队的会话不受影响。
- **F2：Lead 权限收窄。** Coordinator 生效时，Team Lead 不得直接使用文件写入类工具；可继续使用只读工具、团队任务、成员、邮箱、审批、停止和恢复能力。Git 检查、合并、回滚与验证只能通过受控集成能力或明确允许的受限命令执行，且访问范围只能是绑定仓库及已登记成员 Worktree。
- **F3：目标拆解。** Team Lead 接收用户目标后，可以产生一个有固定系统上限的拆解批次。每个任务都必须包含标题、描述、依赖、目标成员或所需角色以及可观察的验收标准；任务标识、顺序、依赖和批次决定必须稳定且可审计。无效依赖、循环依赖、越界数量或不完整任务必须整体拒绝，不得发布部分拆解结果。
- **F4：安全派发。** 任务只有在全部依赖成功后才能派发。系统必须综合成员角色与能力、运行状态、审批状态、当前持有任务和共享容量选择长期成员。不满足条件时任务保留为 pending 并记录有界原因，不得强行启动成员、重复启动成员或超额占用容量。
- **F5：审批与调度决策。** 需要审批的成员继续使用 Phase 14A 的计划请求和结构化批准协议；自动编排不能批准自身请求或绕过待批准状态。Team Lead 可以重新派发、取消、停止或把任务转为人工处理，每次决定都必须持久化并包含有界理由。失败、停止和成员不可用必须阻止不安全的后续派发。
- **F6：持续协调。** Coordinator 可以观察共享任务、成员终态、审批、邮箱通知、容量、运行状态和 Git 变化，并以幂等步骤推进拆解、派发、重新派发和候选判定。同一任务同时只能有一个活动协调动作；恢复时不得自动重放成员工具调用。
- **F7：合并候选资格。** 可合并任务必须关联成员固定 Worktree、已验证的团队与成员归属、提交基线、预期提交范围和预期交付终态。只有任务成功完成、依赖满足、成员进入可信终态且 Worktree 不存在未确认运行时，任务才能成为集成候选。终端成员还必须满足 Phase 14B 验收能力边界。
- **F8：集成计划与顺序。** 系统必须针对一个目标分支和明确基线创建集成批次，检查目标分支与基线是否漂移，并对允许的漂移执行策略化重新验证。候选任务按依赖拓扑顺序合并；同一拓扑层使用稳定顺序。依赖任务必须已成功集成或被明确判定为不影响本任务。任一目标分支同时只能有一个团队集成批次，同一任务同时只能有一个合并尝试。
- **F9：Git 检查与受控操作。** 每个集成步骤在写入前必须检查 Worktree 归属、团队与成员身份、仓库边界、目标分支、基线、工作区状态、提交范围和任务归属。允许自动处理的冲突只能来自预先声明、无歧义且结果可验证的策略。不得执行自动 push、修改远端、创建或合并远端 PR，也不得删除成员 Worktree 或其中未合并的成果。
- **F10：失败原子性。** 任何冲突、检查失败、Git 命令异常、进程中断或提交后验证失败，都必须恢复到该合并操作前可验证的状态，或在无法证明安全恢复时立即标记为需要人工处理。对应任务或集成批次必须失败或转人工，向 Team Lead 返回脱敏的有界诊断，并停止所有后续依赖步骤；不得把部分成功报告为完成。
- **F11：持久化与恢复。** 双开关启用后，拆解批次、派发决定、集成批次、每个集成步骤、Git 操作边界、回滚信息和结果必须使用版本化、严格校验的持久记录。重启后，已确认具有副作用的 Git 步骤不得重放；未完成步骤必须由 journal 判定为可安全继续、需要回滚或需要人工处理。运行中成员继续使用 Phase 14A/14B 的保守中断收敛。
- **F12：严格格式与数据最小化。** Phase 14C 记录必须拒绝未知字段、重复字段、未来版本、截断内容、非法状态转换和越界文本。所有路径继续执行团队根目录包含性以及链接/重解析点检查。持久记录和诊断不得包含密钥、完整 shell 参数、完整会话内容、原始模型内容或未脱敏的 Git/进程异常。
- **F13：可替换边界。** 时间、标识、Git、文件与分支锁、容量、环境变量、进程、等待和 Phase 14B 能力判定都必须可替换测试。自动协调不得依赖忙轮询或真实长时间等待。

## 非功能需求

- **N1：兼容性。** 旧 Phase 14A/14B 团队和未启用 coordinator 的所有功能保持原有行为；新增文件缺失时无需迁移或修复。
- **N2：确定性。** 同一有效输入、成员快照和仓库快照必须产生稳定的任务顺序、派发解释和集成顺序；并发竞争通过持久锁、租约或等价机制确定收敛。
- **N3：安全默认。** 无法证明成员终态、Worktree 所有权、基线、提交范围、journal 状态或恢复安全时，一律不派发、不合并或转人工，不进行猜测修复。
- **N4：可审计性。** 所有自动决定都能关联到团队、用户目标、任务、成员、状态修订和有界原因；所有有副作用的 Git 边界都有开始前状态、结果和恢复判定。
- **N5：隐私与诊断。** 用户可见和持久诊断必须稳定、简洁、脱敏且有长度上限，同时保留足够的错误类别和阶段信息供人工处理。
- **N6：本地性。** 所有协调与集成仅发生在单机已绑定仓库和登记 Worktree 内，不访问或修改远端状态。
- **N7：可测试性。** 单元、集成、并发、崩溃恢复、Git fake 端到端和完整回归可以在无网络、无真实模型、无真实长等待的环境中确定执行。

## 不做的事

- 不支持跨机器、跨用户或分布式团队。
- 不实现成员间实时流式通信或复杂通用 DAG 调度算法。
- 不自动 push，不创建或合并远端 PR，不修改远端分支或远端配置。
- 不删除成员 Worktree，也不清理其中尚未成功集成的成果。
- 不把 Coordinator 的受限 shell 扩展成通用命令执行权限。
- 不改变普通子 Agent、普通成员或未启用团队会话的权限模型。
- 不在恢复时自动重放成员模型请求、成员工具调用或无法确认结果的 Git 副作用。

## 验收标准

- **AC1（F1、N1）：** 双开关任一未开启时，coordinator 动作不可用，不产生任何 14C 状态或后台任务，Team Lead 的直接写入权限与 Phase 14A/14B 相同。
- **AC2（F1、F2）：** 双开关均开启时，仅已绑定团队的 Team Lead 看不到或无法调用文件写入工具，但可使用只读、团队协作和受控 Git 集成能力；其他会话权限不变，越界 shell 或 Git 写操作被拒绝。
- **AC3（F3、F4、F5、N2、N4）：** 自动拆解产生数量受限、完整、无环、稳定且可审计的任务依赖和派发决定；审批成员在批准前不会启动，且任何重新派发、取消、停止或转人工决定均可追溯。
- **AC4（F4、F5、F6）：** 容量不足、依赖未完成、成员繁忙或失败、审批待定和停止请求都会使任务保留 pending 或转入明确终态；并发协调不会重复启动成员或产生两个活动动作。
- **AC5（F7、F8、F9）：** 只有成功完成且通过成员终态、归属、基线、工作区、提交范围和依赖检查的任务进入候选；集成严格按稳定拓扑顺序执行，同一目标分支和任务的并发尝试被排除。
- **AC6（F8、F9、F10、F11、N3）：** 冲突、Git 失败、进程崩溃和重启不会造成重复合并或未报告的部分成功；失败步骤恢复到操作前可验证状态，无法安全恢复时转人工，并阻止后续依赖任务。
- **AC7（F9、N6）：** 自动集成不会 push、修改远端、创建远端 PR、删除 Worktree 或删除未合并成果；所有 Git 访问均限制在绑定仓库和登记 Worktree。
- **AC8（F1、F5、F6、F11、N1）：** Phase 14A/14B 的进程内成员、Windows Terminal 成员、tmux 成员、审批、邮箱、会话恢复、停止、普通子 Agent 和未启用团队的回归全部通过。
- **AC9（F7）：** 在已验收的 Phase 14B 环境中，Windows Terminal 与 tmux 成员可参与端到端编排和集成；在无法证明 Phase 14B 已完成的环境中，这两类成员被明确拒绝且其结果不会成为候选，进程内成员仍可按受限路径运行。
- **AC10（F3—F13、N2—N7）：** 单元、集成、并发、审批、容量、崩溃恢复、路径安全、严格编解码、Git fake 端到端和完整测试套件全部通过；测试不依赖网络、真实模型或真实长等待。
